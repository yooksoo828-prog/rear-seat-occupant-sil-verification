## 1. SIL이란

SIL(Software-in-the-Loop)은 시험 대상 소프트웨어를 호스트 PC 등의 가상 실행 환경에서 실행하고, 모사된 입력·환경과 연결하여 기능과 동작을 시험하는 방식임. 모델에서 자동 생성한 코드뿐 아니라 수작업으로 작성한 코드도 시험 대상이 될 수 있음(Ubiquitous AI Corporation, n.d.). 아래의 모델 기반 개발 사례에서는 모델과 생성 코드의 동등성 확인을, 자율주행 사례에서는 가상 환경과 연결한 소프트웨어의 동작 평가를 주요 목적으로 다루었음.

> [그림 생략] 그림. Shylla 외(2023)의 Fig. 1, V-모델 워크플로에서 MIL·SIL·HIL 시험의 위치 — 논문·데이터시트의 그림이라 저작권 때문에 저장소에 올리지 않음. 원문은 해당 출처를 참조.

그림. Shylla 외(2023)의 Fig. 1, V-모델 워크플로에서 MIL·SIL·HIL 시험의 위치

Shylla 외(2023)는 모델 기반 설계에서 MIL 시험을 마친 제어기 모델로 코드를 생성하고, 이 코드를 시뮬레이션 환경에서 가상으로 실행하면서 여러 입력 조건에서의 성능을 확인하는 것을 SIL이라고 설명하였음. SIL의 목적은 소프트웨어 코드가 실제 모델의 구조와 성능을 그대로 재현하는지 확인하는 것이라고 하였음(p. 2, Sec. II.B). V-모델에서는 소프트웨어 설계 단계에서 SIL로 시스템 모델에서 생성한 코드가 여러 운전 조건에서 견고한지 검증하고, 프로세서가 개발에 포함되면 유닛 시험 단계에서 PIL도 가능하며, 코드를 하드웨어와 합치는 통합 시험 단계에서 HIL로 최종 검증한다고 하였음(p. 2, Sec. II, Fig. 1).

다른 자료도 같은 방향으로 SIL을 정의하였음. Won 외(2025)는 V-모델의 SIL 단계에서 MIL로 검증한 제어기 모델을 양산용 C/C++ 코드 같은 소스코드로 변환하여 컴파일·실행하며, 변환된 코드가 실제 ECU를 모사하는 환경에서 기존 모델과 기능적으로 동일하게 동작하는지 검증하는 것이 주된 목적이라고 하였음(pp. 967–968). J. Kim과 Choi(2024)는 SIL을 SW를 PC상에서 시뮬레이션으로 검증하는 방식이라 하였고 vECU(Virtual Electronic Control Unit)를 사용한다고 하였음(p. 885). Arsie 외(2014)는 SiL 환경이 대상 코드를 이식하여 코드의 정확성을 검증하는 방법을 제공한다고 하였음(p. 223). 자율주행 분야에서 Fei 외(2024)는 SIL 시뮬레이션을 통합 소프트웨어 또는 그 구성요소를 시뮬레이션 도구로 실제 환경에서의 동작처럼 돌리는 것으로 설명하였고, 시험 대상 시스템을 가상 환경에 넣어 시뮬레이션된 센서 입력을 처리하게 하고 그 제어 명령으로 가상 환경의 차량이 움직이는 폐루프로 동작한다고 하였음(pp. 2050–2051).

ISO 26262-6:2018은 소프트웨어 유닛 시험을 실행할 수 있는 환경의 예로 모델 인 더 루프, 소프트웨어 인 더 루프, 프로세서 인 더 루프, 하드웨어 인 더 루프를 나열하였음(9.4.5 NOTE 3, p. 23; ISO, 2018).

## 2. SIL의 구성

이 절의 사례를 종합하면 SIL은 시험 대상 소프트웨어, 시험 입력과 동작 환경을 모사하는 모델, 실행·입출력 연결·결과 평가 환경을 중심으로 이해할 수 있음. vECU와 FMU는 소프트웨어를 실행·연결하는 구현 방식이며, CANoe·CarMaker·Automation Studio 등은 각 연구가 선택한 도구임. 이러한 특정 도구를 모두 갖추는 것이 SIL의 공통 필수 조건은 아님. 아래에서는 각 연구가 이 요소들을 어떻게 구성하였는지 정리하였음.

그림. Shylla 외(2023)의 Fig. 4, 시뮬레이션된 PLC 안의 제어 프로그램과 시뮬레이션 모델을 연결한 SIL 구성

Shylla 외(2023)의 사례에서 SIL은 Simulink 모델에서 자동 생성한 C 코드를 PLC 개발 도구(Automation Studio)로 가져와 시뮬레이션 모드에서 실행하는 방식이었음. 이 모드는 코드를 시뮬레이션된 하드웨어에서 돌리고, 제어 프로그램은 TCP/IP로 물리 시뮬레이션(Industrial Physics)과 입출력을 주고받음. 가져온 코드는 초기화(Init.c), 주기 실행(Cyclic.c), 종료(Exit.c) 파일로 나뉘고, 주기 실행 파일에서 모델의 스텝 함수를 호출함(p. 5, Sec. III.D, Fig. 4). 코드 생성은 생성된 코드가 원래 Simulink 모델의 기능과 성능을 그대로 흉내 낼 때 성공한 것으로 본다고 하였음(p. 4, Sec. III.B).

자율주행 제어 로직을 대상으로 한 Won 외(2025)의 구성은 다음과 같았음. MATLAB/Simulink 모델을 Embedded Coder로 C 코드로 바꾸고 DLL로 빌드한 뒤, Synopsys Silver가 이 DLL로 vECU를 만들고 FMI 2.0 규격의 FMU로 내보냄. IPG CarMaker는 차량 동역학 플랜트 모델, 도로, 주변 차량·보행자·신호등을 제공하고 FMI 마스터로서 FMU와의 공동 시뮬레이션(co-simulation)을 조율함(pp. 969–970, Fig. 3). vECU의 사양은 호스트 컴파일 방식이고 하드웨어 모델링은 해당 없음(NA)이며 운영체제는 Silver가 제공하는 시뮬레이션 OS로 정리되었음(p. 970, Table 2). 이 연구에서는 마스터의 통신 주기와 FMU의 실행 시점을 맞추기 위해 Simulink 모델의 솔버를 고정 스텝으로 지정하였음(p. 969). 이 설정은 해당 툴체인의 구현 조건으로 이해해야 함. FMI 2.0은 통신 시점 사이에 각 하위 모델이 자체 솔버로 계산하는 구조를 허용하므로, FMU 내부의 적분 스텝과 모델 사이의 통신 스텝을 구분해야 하며 가변 스텝 사용 자체가 시간 불일치를 뜻하는 것은 아님(Modelica Association, 2014, Sec. 4.1).

J. Kim과 Choi(2024)는 자신들의 SIL 환경을 FMU(Functional Mock-up Unit), 플랜트 모델, 시뮬레이션 환경으로 구성하였고, Vector CANoe 위에 VCU의 vECU(FMU), Simulink와 Amesim 기반 플랜트 모델, CAN 메시지 처리용 라이브러리를 연결하여 구성하였음(pp. 886–887). 이 vECU는 양산 응용 SW와 기반 SW(BSW)를 합친 형태이며, MCAL과 BSW 계층에서 코드를 수정하므로 실제 ECU의 동작과 차이가 생길 수 있다고 하였음(p. 886).

Fei 외(2024)의 사내 SIL 툴체인(CSPAS)은 ADS 차량의 운동과 센서 모델을 담은 차량 시뮬레이터와 오픈소스 시나리오 재생기 esmini로 구성되며, 시나리오와 도로는 OpenSCENARIO·OpenDRIVE 형식, 주변 정보 교환은 OSI 형식을 따랐음(p. 2051). Jeong 외(2016)는 AUTOSAR 소프트웨어 컴포넌트 코드를 가상 기능 버스(VFB)를 PC에서 시뮬레이션한 계층 위에서 실행하도록 컴파일하여 Code Simulator라는 PC 실행 파일로 만들고, 이를 차량 시뮬레이터(CarSim)와 연결하였음. Code Simulator의 main 함수는 차량 시뮬레이터의 타이머에 동기화됨(pp. 60–62). 이들 구성에서는 대상 하드웨어 대신 호스트 PC가 코드를 실행함.

ISO 26262-6:2018은 모델 기반 개발에서 유닛 시험을 모델 수준에서 한 뒤 모델과 목적 코드 사이의 백투백 비교 시험을 하여 모델의 거동이 자동 생성된 코드와 같은지 확인할 수 있다고 하였음(9.4.5 NOTE 4, p. 23; ISO, 2018). 이 사례들은 제어기 소프트웨어를 대상으로 하며, 센서를 모델로 대신하는 구성은 Fei 외(2024)와 아래 7절의 사례에 한정됨.

## 3. SIL과 HIL의 비교

J. Kim과 Choi(2024)는 SIL이 HIL로 평가할 수 있는 모든 기능을 검증할 수는 없지만, 물리적 하드웨어 없이 가상 환경에서 ECU 기능을 시뮬레이션하여 개발 초기에 SW 오류를 검증할 수 있고 HIL 대비 검증 환경 구축 비용이 저렴하다고 하였음. 또 실시간이 아닌 시뮬레이션 시간(simulation time)을 쓰므로 검증 시간을 줄일 수 있다고 하였음(pp. 885–886). 구축 비용과 시간을 수치로 비교한 결과는 이 논문에서 확인되지 않았음. 한편 SIL에서는 하드웨어의 영향을 받는 성능·신뢰성 등을 검증할 수 없으므로 기존 HIL 시험 항목 가운데 SIL로 검증 가능한 항목을 골라야 한다고 하였고, 그 결과 시동·구동 등의 기능에 대한 시험 항목 379개를 선별하였음(p. 887).

같은 논문은 상용차 VCU에 대해 이 379개 항목을 HIL과 SIL로 각각 시험하여 결과를 비교하였음. HIL과 SIL 모두 Pass 288개, Fail 91개였고, 항목별로는 377개가 일치하여 일치율 99.47%였음. 불일치 2건은 각각 HIL Fail·SIL Pass 1건, HIL Pass·SIL Fail 1건이었음(p. 887, Table 1). 불일치의 원인은 두 가지였음. 첫째, 가속 페달 센서(APS)의 아날로그 값을 디지털로 바꾸는 변환 표가 불연속이어서 SIL의 가상 VCU에는 0%, 20%, 100% 입력에 대해서만 if-else 문으로 구현되었고, 그 결과 APS 고장 주입 시험에서 SIL은 Pass, HIL은 Fail이 되었음(pp. 887–888). 둘째, FMU가 CANoe의 시뮬레이션 시간이 아니라 Windows 시간을 기준으로 동작하여, 일정 시간 동안 상태를 유지하는지 보는 시험에서 PC 상태에 따라 결과가 달라졌음(p. 888). 표 전체를 코드로 생성해 넣고 FMU가 시뮬레이션 시간 기준으로 동작하도록 바꾼 뒤에는 모든 시험 항목에서 일치하는 결과를 얻었다고 하였음(pp. 889–890). 이 결과의 99.47%는 선정된 379개 항목에서 SIL과 HIL의 Pass·Fail 판정이 일치한 비율임. 이 사례는 상용차 VCU 두 차종을 대상으로, 결과 비교를 통해 신호 변환과 시간 기준의 구현 문제를 찾아 개선한 사례로 활용할 수 있음.

Won 외(2025)는 SIL을 MIL, HIL과 구분하였음. 저자들은 MIL을 제어 모델의 타당성을 빠르게 확인하는 단계로 설명하고, 자신들의 vECU 기반 SIL에서 연산·통신 지연과 소프트웨어 상호작용의 영향을 시험하였음. 이러한 평가 범위는 vECU와 시뮬레이션 환경에 구현된 시간·통신 특성에 따라 달라지므로, vECU를 사용한다는 사실만으로 실제 ECU의 지연이 자동으로 재현되는 것은 아님. 이후 단계인 HIL은 ECU를 실시간 시뮬레이션 환경에서 검증한다고 하였음(p. 968). Shylla 외(2023)도 V-모델에서 SIL을 소프트웨어 설계 단계에, HIL을 통합·최종 검증 단계에 두었음(p. 2).

## 4. SIL의 장점

Shylla 외(2023)는 가상 모델 시험으로 하드웨어 없이, 또는 최소한의 하드웨어로 새 응용을 검증할 수 있다고 하였음. 현장에서 결함을 고치는 것이 개발 중에 고치는 것보다 훨씬 비싸며, 물리 시제품이 필요 없어져 개발 기간과 비용이 줄어든다고 서술하였음(p. 1). 이 서술은 모델 기반 설계의 가상 시험 전반에 대한 것이고 SIL만의 장점으로 따로 제시된 것은 아님. 시험을 계속 돌리며 결함을 일찍 고칠 수 있다는 점도 모델 기반 설계의 장점으로 꼽았음(p. 6). 비용과 기간을 수치로 비교한 결과는 이 논문에서 확인되지 않았음.

J. Kim과 Choi(2024)는 SIL이 HIL보다 개발 초기에 오류를 검증할 수 있고 환경 구축 비용이 낮으며 시뮬레이션 시간을 쓰므로 검증 시간을 줄일 수 있다고 하였고(pp. 885–886), 결론에서 HIL 시험 전에 SIL로 조기 검증하는 것이 의미 있음을 확인했으며 SIL 활용으로 차량 개발에 필요한 비용과 시간을 줄일 수 있게 되었다고 하였음(p. 890). Jeong 외(2016)는 실차와 HIL 시험이 ECU용 실행 파일을 필요로 해 개발 후반에야 가능한 반면, SIL은 ECU와 시스템 구성 전에 소프트웨어 컴포넌트를 PC에서 시험할 수 있다고 하였음. 이 방법으로 자동 긴급제동 소프트웨어를 눈길·빙판길 같은 노면 마찰 조건에서 시험하고 코드를 고쳐 제동 성능을 개선하였으며, 실제로 시험하기 어려운 극한 조건을 시험할 수 있다고 하였음(pp. 59–63). Won 외(2025)는 vECU가 소프트웨어와 하드웨어의 개발 주기를 분리하여 개발 속도를 높일 수 있고, 실제 하드웨어로는 위험하거나 비용 부담이 큰 시나리오를 제약 없이 검증할 수 있다고 하였음(pp. 969–970). Fei 외(2024)는 SIL이 유연성과 효율 덕분에 자율주행차의 빠른 개발과 시험에 널리 쓰이며 드물고 위험한 상황을 포함한 폭넓은 시나리오를 평가할 수 있다고 하였음(pp. 2050–2051).

ISO 26262-6:2018의 정보 제공용 부속서는 모델 기반 개발에서 모델로 소프트웨어 유닛을 개발하면 코드를 모델에서 바로 생성할 수 있고, 일관성 점검을 자동화하며 시뮬레이션이나 MIL/SIL 시험으로 소프트웨어 유닛을 검증할 수 있다고 하였음. 코드 생성기에 대한 신뢰 정도에 따라 자동 코드 생성이 수작업 코딩보다 코딩 오류 위험을 낮출 수 있다고도 하였음(B.3.3, p. 38; ISO, 2018).

## 5. ISO 26262과 SIL

ISO 26262-6:2018의 11.4.1 Table 13은 소프트웨어 안전 요구사항 검증의 시험 환경으로 HIL, ECU 네트워크 환경, 차량을 나열하였고 SIL은 항목에 없음(p. 29). 소프트웨어 유닛 시험(9.4.5, p. 23)과 통합 시험(10.4.7, pp. 27–28)에서는 시험 환경이 대상 환경을 고려하여 목적 달성에 적합해야 하고, 대상 환경에서 시험하지 않으면 소스·목적 코드의 차이와 시험 환경·대상 환경의 차이를 분석하여 이후 단계의 대상 환경 시험에서 추가 시험을 정해야 한다고 규정함. 두 조항의 NOTE는 시험 환경의 예로 SIL을 포함해 MIL, PIL, HIL을 들었음(ISO, 2018).

이를 종합하면 ISO 26262-6은 SIL을 유닛 시험 환경의 한 예로 인정하되, 대상 환경과의 차이 분석과 추가 시험을 요구함. 또한 Table 13에는 SIL이 없으므로 SIL만으로 Table 13이 요구하는 시험을 대신할 수 있다는 근거는 읽은 조항에서 확인되지 않았음(해석). 이 해석은 7단계에서 다시 다룸.

## 6. SIL의 한계

SIL의 한계는 자료마다 다른 측면에서 서술되었음.

첫째, 시뮬레이션 모드의 주기와 시간 정합성임. Shylla 외(2023)는 자신들이 사용한 Automation Studio의 SIL 시뮬레이션 모드에서 주기를 보통 100 ms로 설정하며 더 짧은 주기는 불가능할 수 있다고 하였음(p. 5, Sec. III.D). 이는 해당 도구와 실행 모드의 조건이며, SIL 전체의 최소 주기나 공통 성능 한계를 나타내는 수치는 아님. 같은 논문은 크레인 속도를 높이면 PLC를 연결한 HIL 시험에서 진동이 나타날 수 있는데, MIL에서는 모델이 만족스럽게 동작했더라도 PLC가 기준점 도달 정보를 받는 데 시간이 걸리기 때문이라고 하였고, 이 진동은 Automation Studio의 주기를 100 ms에서 10 ms로 줄여 줄일 수 있다고 하였음(pp. 5–6, Sec. III.E). 이 서술은 MIL과 HIL의 차이에 대한 것이며 SIL에 대한 직접적인 진술은 아님. 시뮬레이션 모드의 주기와 대상 하드웨어가 요구하는 주기가 다를 수 있다는 점은 두 서술을 겹쳐 읽은 해석임. 한편 J. Kim과 Choi(2024)는 실행 주기의 길이와 별개로, 연결된 도구 사이의 시간 기준 불일치를 보고하였음. FMU가 Windows 시간으로 동작하여 CANoe 시뮬레이션 시간과 맞지 않았고, 같은 시험이 PC 상태에 따라 다른 결과를 냈음(p. 888). 이 논문은 결론에서 SIL은 PC에서 제어기가 동작하므로 실시간 장비와의 차이가 분명히 존재하며 PC 종류와 상태에 따라 검증 결과가 달라질 수 있다고 하였음(p. 890).

둘째, MIL 대비 SIL 결과의 차이임. Won 외(2025)는 vECU를 만든 FMU가 블랙박스 구조여서 MIL에서는 없던 오차가 SIL에서 나타날 수 있다고 하였음(p. 968). 자율주행 제어 로직을 FMU 하나로 통합한 경우, 일부 분산한 경우, 완전히 분산한 경우를 MIL과 비교한 결과, FMU를 더 세분할수록 NRMSE가 전반적으로 커지고 일부 신호에서 Pearson 상관계수가 떨어졌음. 조향각과 요레이트에서 상대적으로 큰 오차가 나서 횡방향 제어가 이런 구조적 특성에 더 민감하다고 하였고, 그럼에도 Pearson 상관계수가 0.7보다 크면 강한 양의 상관으로 분류하므로 두 데이터는 강한 상관을 가진다고 보았음(pp. 975–976, Table 4). 시나리오 B에서 완전 분산형 vECU의 NRMSE는 조향각 2.469(%), 요레이트 1.586(%)이었고 Pearson 상관계수의 최솟값은 조향각의 0.80066이었음(p. 975, Table 4). 저자들은 이 차이를 통신 지연과 연산 비동기성이 누적되어 실제 ECU 아키텍처의 특성을 반영한 결과로 해석하였음(p. 976).

셋째, 시험 가능한 항목의 범위임. J. Kim과 Choi(2024)는 SIL로는 하드웨어의 영향을 받는 성능·신뢰성 등을 검증할 수 없다고 하였고(p. 887), vECU가 MCAL과 BSW 계층의 코드를 수정하므로 실제 ECU와 차이가 생길 수 있다고 하였음(p. 886). 두 차종, 379개 결과만 비교했으므로 파악되지 못한 오류가 있을 수 있다는 점도 한계로 적었음(p. 890). Jeong 외(2016)는 AUTOSAR의 RTE와 BSW 대신 하드웨어와 무관한 VFB를 시뮬레이션하여 시험하였으므로, 이 방식의 시험 범위에는 각 ECU의 하드웨어 추상화와 운영체제가 들어가지 않는다고 읽을 수 있음(해석; 근거 pp. 60–61).

넷째, 센서 모델의 충실도와 시뮬레이션 툴체인의 검증임.

Fei 외(2024)는 SIL 시뮬레이션의 툴체인을 검증하는 것이 시뮬레이션이 ADS의 거동을 재현한다는 신뢰를 얻기 위한 전제이자 필수 단계라고 하였고, 자율주행 3단계 시스템의 UN-R157 요건을 충족하려면 해당 적용 영역에서 시뮬레이션 툴체인과 물리 시험 사이의 상관을 확립해야 한다고 하였음(p. 2050). 이 연구의 SIL 환경은 이상적(ideal) 센서 모델을 썼는데, 이 모델은 센서를 모사하려는 것이 아니라 시뮬레이션된 시나리오의 물체와 도로 요소를 보고하는 것이며 시야각(FOV)과 가려짐 효과를 포함한다고 하였음(p. 2051). 시험장 시험과 맞추기 위해 이상적 센서의 최대 범위를 시험 차량의 성능에 맞게 보정하였음(p. 2054). 정지 목표물, 끼어들기, 끼어나가기 세 시나리오를 시험장 반복 시험과 비교한 결과 Pearson 상관계수는 대부분 0.9를 넘어 강한 상관을 보였으나, 상대 RMSE는 신호와 시나리오에 따라 달랐음. 종방향 속도는 평균 반복 기준 2.07–6.05%로 우수했고, 목표물까지의 거리는 7.35–14.20%로 양호했으며, 종방향 가속도는 14.70–28.42%로 양호에서 보통 수준이었음. 어려운 끼어나가기 시나리오에서는 시험장 반복 두 번의 결과가 좋지 않아 가속도 관련 신호의 정확도에 영향을 주었다고 하였음(pp. 2056–2057, Tables II–IV). 이 결과는 이상적 센서 모델을 포함한 자율주행 ADS 툴체인의 거동을 시험장 결과와 비교한 것임. Pearson 상관계수는 신호가 함께 변화하는 정도를, 상대 RMSE는 두 신호 값의 차이를 평가하므로, 높은 상관계수만으로 값의 크기나 편향까지 일치한다고 볼 수는 없음. 본 프로젝트에서는 이러한 결과 비교 절차와 지표 선택을 참고할 수 있음.

ISO 26262-6:2018의 정보 제공용 부속서는 모델 기반 개발에서 모델로 표현되지 않는 설계 측면은 다른 형태로 문서화하지 않으면 놓칠 수 있고, 모든 시험이 불완전한 모델에서 도출되면 백투백 시험으로도 드러나지 않을 수 있다고 하였음. 기능만 모델링하면 견고성 같은 안전 관련 코드 특성이 구현되지 않을 수 있다고도 하였음(B.3.3, p. 38; ISO, 2018). 플랜트 모델을 쓰는 시험에서는 검증에 쓰는 모델의 적합성 근거가 없으면 관련 결과의 타당성이 의심스러울 수 있다고 하였음(B.3.5, p. 39; ISO, 2018). 이 문장은 HIL로 폐루프 제어기를 시험하는 맥락에서 적혔으나, 센서를 모델로 대신하는 SIL에도 같은 문제가 생길 수 있다고 읽을 수 있음(해석).

## 7. 초음파 센서에 적용된 SIL

D.-J. Kim 외(2024)는 3D 초음파 센서 개발의 일환으로 근거리·저속 자율주행 시스템 기반의 3D 초음파 센서 평가 환경을 SIL로 구축하였음. 자율주행 시뮬레이션 소프트웨어 MORAI SIM: Drive와 미들웨어 ROS Melodic을 썼고, 이 시뮬레이터가 3D 초음파 센서를 지원하지 않아 지원하는 센서인 라이다의 시야각(FoV)을 수정하여 3D 초음파 센서를 모사하였음. 모사한 센서의 성능을 확인하기 위해 국제 표준인 ISO 문서에 기반한 정적 물체 검출 시나리오(정지 보행자, 정지 장애물, 정지 차량)를 만들어 시뮬레이션에 활용하였음. 센서에서 물체까지의 최단 거리와 점의 위치 속성값(x, y, z)을 얻었고, 최단 거리를 차량 제어 노드에 ROS 토픽으로 보내 일정 거리에 따른 가감속 명령을 시뮬레이션 내 차량에 전달하였음(p. 539). 이 자료는 한 쪽짜리 초록이며 모사한 센서의 정량적 정확도는 초록에서 확인되지 않음. 초음파의 에코·반사 특성이나 잡음의 모델링 여부는 공개된 초록에 설명되어 있지 않음. 이 연구는 지원되지 않는 센서를 기존 가상 센서의 시야각 조정으로 구현하고, 거리 정보를 제어 로직과 연결해 시나리오를 실행한 평가 환경 구성 사례로 활용할 수 있음.

초음파 모델의 충실도를 검토하기 위한 보완 자료로는 Zhu 외(2025)의 HIL 연구가 있음. 저자들은 현장 운영 시험의 비용과 효율 문제를 설명하고, 자신들이 검토한 기존 MIL 모델과 단순한 가우시안 잡음 추가 방식이 실외 초음파 성능을 충분히 재현하지 못하였다고 보았음(pp. 17055–17056). 이에 온도·습도·기압의 영향을 반영한 모델과 실제 초음파 센서를 연결한 HIL 시험대를 구성하였음. 이 논문은 SIL의 직접 적용 사례와 구분하여, 초음파 센서 모델에 어떤 환경 요인을 반영할지 검토하는 자료로 활용함. 관련 HIL 구성은 HIL 문서에서, 모델의 충실도는 7단계 SIL의 한계에서 다시 다룸.

센서 신호를 입력으로 받는 제어 시스템의 시험 방법으로는 Arsie 외(2014)가 있음. 이 논문은 측정 기반 복합 제어 시스템의 기능 검증을 위해, 시험 자극(입력 데이터)을 측정 시스템의 동작 범위 안에서 시간과 데이터 의존성을 재현하는 통계 기법으로 자동 생성하는 방법을 제시하였고, 공연비 제어 시스템 사례로 평가한 결과 이 방법이 SIL 환경에서 임베디드 제어 시스템의 자동 기능 시험에 적합하다고 초록에 적었음(p. 222). 사례의 제어 소프트웨어는 순환 신경망(RNN) 기반 공연비 제어기로, 엔진 회전수와 흡기관 압력 센서 신호를 입력으로 받아 분사 시간을 출력함(p. 228). 시험 신호는 엔진 시험대에서 스로틀 개도 프로파일 20개(각 10단 계단 입력)를 구동해 얻은 과도 응답 200개에서 입력 변수의 분포와 상관을 추정하고, 라틴 하이퍼큐브 샘플링과 상관 유도로 생성하였음(pp. 228–231). 데이터 수집 하드웨어의 양자화 잡음을 모사하려고 생성한 신호에 임의의 잡음을 더했음(p. 231). 약 180초 길이의 입력 시간 이력 100개로 시험한 결과 추정 공연비는 이론 공연비의 ±5% 안에, 평균은 ±1% 안에 들었고, 저자들은 이를 시험 방법이 그럴듯한 과도 상태 열을 재현한다는 지표로 해석하였음(pp. 231–232). 이 해석은 시험 대상 소프트웨어를 기준(golden standard)으로 본다는 전제에 기대며, 소프트웨어에 버그가 있을 때 오차가 이보다 커지는지는 이후 연구로 남겼음(p. 232). 사례 절은 실행 환경을 SIL이라고 따로 명시하지 않았고, SIL 적합성은 초록의 서술임. 이는 센서 신호를 입력으로 받는 제어 소프트웨어의 시험이며 초음파 센서의 감지 성능을 시험한 사례는 아님.

문헌에서 본 프로젝트에 활용할 수 있는 방법은 평가 환경 구성, 시험 입력 생성, 결과 비교로 정리할 수 있음. D.-J. Kim 외(2024)는 가상 센서의 거리 출력을 제어 로직과 연결하는 방법을, Won 외(2025)와 J. Kim과 Choi(2024)는 시험 대상 소프트웨어와 환경 모델을 연결하고 실행 시간을 맞추는 방법을 보여 줌. Arsie 외(2014)는 입력의 분포와 시간·변수 간 의존성을 고려한 시험 신호 생성에, J. Kim과 Choi(2024)와 Fei 외(2024)는 기준 결과와의 비교 및 불일치 원인 분석에 참고할 수 있음. 이러한 역할 구분은 문헌을 종합한 프로젝트 활용 관점임. 조사 범위에서 차실 안 점유 감지나 HC-SR04 자체에 대한 SIL 사례는 확인하지 못하였으며, 개별 문헌의 성능 수치는 해당 연구 조건에서 얻어진 결과로 구분하여 사용함.

## 8. 결론

SIL은 시험 대상 소프트웨어를 호스트 PC 등의 가상 환경에서 실행하고, 모사된 입력·환경과 연결하여 동작을 시험하는 방식임(Fei et al., 2024; Ubiquitous AI Corporation, n.d.). 모델 기반 개발에서는 모델과 자동 생성 코드의 동등성을 확인하는 데 활용되며(Shylla et al., 2023; Won et al., 2025), 수작업 코드의 시험에도 활용할 수 있음(Ubiquitous AI Corporation, n.d.). 구성은 코드를 호스트 PC에서 가상 ECU(vECU)나 시뮬레이션 모드로 실행하고 플랜트 모델과 연결하는 형태였음(Jeong et al., 2016; J. Kim & Choi, 2024; Won et al., 2025). 상용차 VCU의 379개 시험 항목에서 SIL과 HIL의 결과는 377개가 일치하였고 불일치 2건은 센서 신호 변환 표의 구현과 시간 기준 설정에서 비롯되어 수정 후 해소되었음(J. Kim & Choi, 2024). SIL은 HIL보다 이른 시기에 낮은 비용으로 시험할 수 있다고 서술되었으나 수치 비교는 확인되지 않았고, 하드웨어의 영향을 받는 성능·신뢰성은 시험할 수 없음.

한계로는 시뮬레이션 주기와 시간 기준의 정합성(Shylla et al., 2023; J. Kim & Choi, 2024), MIL 대비 SIL의 차이(Won et al., 2025), 센서 모델이 이상적이어서 시험장 결과와 맞추려면 보정과 상관 검증이 필요한 점(Fei et al., 2024)이 제시되었음. ISO 26262-6:2018은 SIL을 소프트웨어 유닛 시험 환경의 예로 들면서 대상 환경과의 차이 분석을 요구하고, Table 13의 시험 환경에는 SIL이 없음(ISO, 2018). SIL만으로 이를 대신할 수 있다는 근거는 읽은 조항에서 확인되지 않았음(해석).

초음파 분야에서는 기존 가상 센서의 시야각을 조정하고 거리 출력을 제어 로직과 연결한 SIL 평가 환경이 보고되었음(D.-J. Kim et al., 2024). 본 프로젝트에서는 이 사례를 가상 센서와 판단 로직의 연결에 참고하고, 다른 SIL 연구에서 제시한 실행 환경 구성·시간 동기화, 입력 신호 생성, 결과 비교 방법을 함께 활용할 수 있음(Arsie et al., 2014; Fei et al., 2024; J. Kim & Choi, 2024; Won et al., 2025). Zhu 외(2025)의 HIL 연구는 초음파 모델에 반영할 환경 요인을 검토하는 보완 자료로 활용함. 본 프로젝트는 하드웨어 없이 SIL로 검증하기로 하였으므로 이 문서의 내용은 4단계 비교표에서 HIL과 나란히 쓰고, 센서 모델의 충실도와 대상 환경과의 차이는 7단계 SIL의 한계에서 다시 다룸.
