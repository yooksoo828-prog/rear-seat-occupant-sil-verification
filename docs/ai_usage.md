# AI 활용 방안 — 이해하기 위해 쓰고, 확인하며 쓴 방법

> **초안** — 2026-11-25. AI(Claude)가 팀장의 요구로 작성하고, 팀장의 설명(2026-11-25)을 반영함. 팀 확인 전.
> 근거는 두 종류로 나눠 표시한다. **[기록]** 은 저장소(커밋, Pull Request, 문서)에서 확인되는 사실이고, **[진술]** 은 팀장이 직접 설명한 것으로 저장소에서는 확인되지 않는다. 둘을 섞지 않았다.

## 3. 문헌 선별 — 사람이 한 판단
요구사항을 AI가 구체적으로 도출하도록 하기 위해, 근거 문헌을 먼저 모았다.

1. AI에게 관련 문헌을 조사하게 했다. [진술]
2. 논문을 처음부터 끝까지 읽을 수 없어 **초록, 범위, 결론** 등 데이터베이스 초안이 제공한 내용을 읽었다. [진술]
3. 그 내용으로 **우리 프로젝트의 목표와 목적에 필요한 문헌과 필요하지 않은 문헌을 사람이 구분**해 AI에 제공했다. [진술]
4. AI는 그 근거 문헌과 프로젝트의 목표·목적에 맞춰 요구사항을 도출했다. [진술]

결과물은 `docs/references/`에 있다. 문서 13개와 근거 출처 42건의 연결이 [기록]으로 남아 있다(`source_map.md`).

## 7. AI가 하지 않는 것
1. 사실이 아닌 기록(합의, 승인, 전달, 실행 시각)을 만들지 않는다. 확인되지 않은 것은 "미실시"로 남긴다.
2. 승인과 합의를 대신하지 않는다. AI 검토는 "충족" 판정이 아니다.
3. 모르는 사실을 채우지 않는다.
4. 결과를 본 뒤 합격 기준을 바꾸지 않는다(불합격 3건 그대로 기록).
5. 개인정보와 저작권을 지킨다. 팀원 실명 마스킹, 대화 캡처 미업로드, 논문 그림 16개와 PDF 미업로드.

| 사례 | 내용 | 처리 |
| --- | --- | --- |
| **요구사항 도출을 AI에 의존** | 요구사항 수치를 팀이 독립적으로 도출하지 않았고, 처음 해 보는 검증이라 요구사항에 대한 이해도가 낮은 상태에서 AI가 도출함 [진술] | 근거 문헌을 사람이 선별해 제공하고, 수치마다 근거 구분(`[문헌]` `[프로젝트 선택]` `[프로젝트 가정]` 등)을 표기해 **출처를 투명하게** 함 |
| 이해와 수행의 차이 | AI가 작업을 쉽게 해 준 것과 팀이 그것을 이해하는 것은 다름 [진술] | 이해를 높이기 위해 AI와 대화하며 개념을 익히는 쪽으로 사용 |

| 낡은 문구 방치 | 공통 정보 표의 승인 기록을 갱신하지 않음. 팀장의 질문으로 확인 | 하단 추가 기록으로 명시 |
| 승인 시각 | PR #9의 두 번째 승인이 병합 17초 뒤에 제출됨 | 체크리스트에 사실대로 기록 |

## 9. 예상 질문과 답
> **주의**: 아래 "답"은 위 기록과 설명에 맞춘 **초안**이다. 말씀하실 때는 **본인이 실제로 한 것만** 말하고, 기억과 다르면 고쳐서 말할 것.

**Q. AI는 어떻게 썼나요?**
A. Claude를 썼습니다. 처음에는 검증을 어떻게 하는지 몰라서 "다 해 달라"고 맡겼습니다. 하지만 이해가 생기면서 AI와 대화하며 방향을 정했고, ISO 29119를 테일러링해 따르는 것과 GitHub로 형상 관리하는 것을 그 과정에서 정했습니다. 저에게 AI는 일을 대신 시키는 도구라기보다 이 프로젝트의 바탕이 되는 검증 개념을 알아가는 도구였습니다.

**Q. 요구사항은 누가 만들었나요?**
A. AI가 도출했습니다. 처음 해 보는 검증이라 요구사항을 직접 만들 이해도가 부족했습니다. 대신 AI가 근거가 될 문헌을 조사하게 하고, 저희가 초록, 범위, 결론을 읽으며 프로젝트에 필요한 문헌과 필요하지 않은 문헌을 골라 제공했습니다. 요구사항은 그 문헌과 프로젝트의 목표에 맞춰 나왔고, 수치마다 문헌에서 왔는지, 저희 선택인지, 가정인지 표시해 두었습니다.

**Q. 직접 한 것은 무엇인가요?**
A. 주제와 SIL 검증 방향을 정했고, 문헌을 선별했습니다. 시험 실행 전에 비어 있던 입력 항목 8개를 결정했고, 결과가 나온 뒤에는 같은 높이 화물을 구분하지 못하는 한계를 알고리즘을 고치지 않고 받아들였으며, 온도 보정 채택과 마감에 따른 범위 축소를 결정했습니다. 산출물은 AI 느낌이 강해서 제가 직접 고쳤습니다.

**Q. AI가 쓴 코드를 어떻게 믿나요?**
A. 제가 확정한 기준선 상수 87개를 코드 값과 대조해서 하나라도 다르면 시험이 실행되지 않게 했습니다. 시험을 두 번 돌려 같은 결과인지, 다른 컴퓨터에서도 같은지 확인했고, GitHub이 변경마다 자동으로 다시 검사합니다.

**Q. AI가 틀린 적은 없나요?**
A. 있었습니다. 증거가 없다고 잘못 판단한 적, 검증 스크립트가 범위 표기를 잘못 읽은 적, 승인 후 갱신하지 않은 낡은 문구를 남긴 적이 있고 모두 기록해 두었습니다.

**Q. 팀원들은 어떻게 참여했나요?**
A. 문*호 팀원은 소프트웨어 검증 실무 경험으로 제 질문에 답하고 아이디어를 주셨고, 저는 그것으로 AI에게 더 풍부한 요청을 했습니다. 강**엘 팀원은 AI가 쓴 보고서와 내용을 검토하고 수정하는 쪽을 맡았습니다. 두 분 모두 Pull Request에서 승인했습니다.

**Q. AI 없이도 가능했을까요?**
A. 이 일정과 이해도로는 어려웠을 것입니다. 다만 AI가 작업을 쉽게 해 준 것과 제가 그 과정을 이해하는 것은 다르다고 생각해서, 개념을 익히고 결과를 직접 고치며 확인하는 데 시간을 썼습니다.
