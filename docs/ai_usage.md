# AI 활용 내역 — 검증 개념을 익히고 결과를 검증하며 활용한 과정

> 이 문서는 팀장의 설명을 바탕으로 AI(Claude)가 정리했고, 괄호 안의 파일은 저장소에서 확인할 수 있는 근거 위치이다.

## 1. 활용 배경과 기본 방향

이번 프로젝트에서 저희 팀은 Anthropic의 **Claude**를 활용했습니다. 처음부터 AI에 모든 작업을 맡기려던 것은 아니었으나, 주제(SIL 검증)를 정한 직후에는 실제 현업의 소프트웨어 검증 흐름과 산출물 체계를 잘 몰라 어디서부터 손을 대야 할지 막막했습니다.

초기에는 전체적인 틀을 잡기 위해 AI에 크게 의존했습니다. 하지만 AI가 만든 초안을 읽고 되묻고, 검증 실무 경험이 있는 팀원에게 물어 가면서 검증의 기본 개념과 절차가 잡히기 시작했고, 이후에는 **AI와 대화를 주고받으며 방향을 조율하고, 결과물을 직접 확인·수정하는 방식**으로 바뀌었습니다. 저희에게 AI는 단순히 문서를 대신 써 주는 도구가 아니라, 생소한 검증 분야의 개념을 익히고 구현 속도를 높이기 위한 보조 수단이었습니다.

| 구분 | 주요 내용 |
| --- | --- |
| **활용 도구** | Claude (Anthropic) |
| **AI 활용 영역** | 근거 문헌 탐색 보조, 요구사항(SR) 초안 도출, SIL 시험 코드와 검증 스크립트 작성, ISO 29119 기반 문서 초안 작성, 수치 대조, 제출물 초안 |
| **팀 직접 수행 영역** | 프로젝트 주제 선정, 근거 문헌 선별, 검증 표준(ISO 29119) 테일러링과 GitHub 형상 관리 체계 결정, 비어 있던 입력 항목(D1~D8) 확정, 산출물 검토·수정, Pull Request 승인 |
| **품질 통제 방식** | 사람이 확정한 기준선 상수 87개와 코드의 자동 대조, GitHub Actions 자동 검사, 팀원 검토와 Pull Request 승인 |

## 2. 역할 분담 및 팀 협업 방식

모든 팀원이 AI를 똑같이 사용한 것은 아닙니다. 각자의 강점에 맞춰 역할을 나누어 AI의 한계를 보완했습니다.

* **팀장 (AI 활용과 기준 확정):** Claude와의 반복적인 대화로 검증 프로세스를 익히고, 요청을 구체화하며 문서와 시험 코드 초안을 이끌어냈습니다. 시험 실행 전에 비어 있던 입력 기준을 확정했고, AI 느낌이 강하게 남은 최종 보고서를 직접 고쳤습니다(커밋 `a5c63ca`, 본문 28줄 변경).
* **문*호 팀원 (실무 경험 기반 방향 제시):** AI는 거의 사용하지 않는 대신, 소프트웨어 검증 실무 경험을 바탕으로 팀장의 질문과 궁금한 점에 답하고 아이디어를 주었습니다. 이 도움으로 AI에게 더 구체적이고 풍부한 요청을 할 수 있었습니다.
* **강**엘 팀원 (산출물 검토와 품질 보완):** AI를 직접 쓰지 않았고, AI가 작성한 보고서와 내용을 검토하고 수정하는 일을 맡아 산출물의 완성도를 높였습니다.

AI 활용은 투명하게 남겼습니다. 적합성 선언문(`docs/29119/00_conformance_declaration.md` 2절)에 문서와 코드 작성에 Claude를 사용했음을 밝혔고, 병합 커밋을 제외한 **모든 커밋**에 `Co-Authored-By: Claude`를 표기했습니다. 최종 반영은 두 팀원이 Pull Request(#5, #7, #9)를 검토해 승인하는 절차를 거쳤습니다.

## 3. 단계별 활용 과정과 주요 의사결정

### ① 근거 문헌 선별과 요구사항 도출

프로젝트 초기에는 시간도 부족하고 요구사항 도출 경험도 적어 AI의 도움을 받았습니다. 다만 근거 없는 수치가 만들어지지 않도록 사람이 먼저 문헌을 걸러냈습니다.

1. Claude로 SIL 검증과 관련 분야의 문헌을 조사했습니다.
2. 논문을 처음부터 끝까지 읽기는 어려워 각 문헌의 **초록, 연구 범위, 결론**을 중심으로 읽었습니다.
3. 읽은 내용으로 **프로젝트의 목표와 목적에 필요한 문헌과 필요하지 않은 문헌을 직접 구분**해 AI에 제공했습니다.
4. 선별된 문헌을 근거로 AI가 요구사항(SR-01~SR-14)과 세부 수치를 도출했고, 각 수치가 어디서 왔는지 알 수 있도록 `[법규]`, `[문헌]`, `[프로젝트 선택]`, `[프로젝트 가정]`으로 출처를 구분해 표기했습니다(`deliverables/Requirements_Specification_SR-01-14_v1.0.docx`).

정리된 문서 13개와 근거 출처 42건의 연결은 `docs/references/source_map.md`에 있습니다.

### ② 표준 테일러링과 주요 기준 확정

검증 절차를 이해하게 되면서 표준과 형상 관리 체계를 직접 정했습니다. 문서 체계는 **ISO/IEC/IEEE 29119**를 프로젝트 규모에 맞게 테일러링해 따르기로 했고, 산출물과 코드의 이력 관리와 자동 검증은 **GitHub** 중심으로 운영하기로 결정했습니다.

AI가 준비한 초안에서 비어 있던 부분은 시험을 돌리기 전과 진행 과정에서 팀장이 결정하고 승인했습니다.

* **시험 전 입력 기준 확정 (2026-11-11, `sil_main/baseline/baseline_v1.0.json`):** 정의가 비어 있던 8개 항목(D1~D8)을 확정했습니다. 예를 들어 실제 치수 근거가 없는 항목은 가상 반사면으로 대체하되 원 조건의 결과로 세지 않기로 했고(D1), 불리한 시험 결과도 그대로 기록하며 SR-09 전체 충족을 선언하지 않기로 했습니다(D3). 합격 기준은 결과를 보기 전에 고정했습니다(D6). D1~D8의 내용은 AI가 준비한 항목에 대해 팀장이 결정하고 승인한 것입니다.
* **역할 배정과 한계 수용 (2026-11-12 ~ 11-13):** AI가 제안한 역할 배정을 확인했습니다(`docs/29119/plan/TP-01.md` 7.2.9.2). 시험에서 나온 TC-04b(같은 높이 화물 구분 불가, 300/300 오검출)는 알고리즘을 바꾸지 않고 **현재 모델의 한계로 수용**하기로 했습니다. 온도 보정은 채택하고, 완료 기준은 결과를 본 뒤 낮추지 않기로 했습니다(`docs/29119/incidents/`, `TP-01.md`).
* **실행 환경과 범위 조정 (2026-11-17 ~ 11-21):** Python·numpy 버전 차이를 허용하기로 하고(`docs/29119/environment/TER-01.md`), 팀장 PC에서도 같은 결과가 재현되는지 확인했습니다(`TRR-01.md`). 제출 마감을 고려해 범위를 줄인 기준선 v1.1을 확정했습니다(`baseline_v1.1.json`, `docs/29119/status/TS-02.md`).

## 4. AI 산출물 검증 및 통제 체계

AI가 작성한 코드(SIL 시험 하니스 TC-01~TC-16, 통계 판정 등)와 문서를 그대로 믿지 않기 위해 여러 겹의 통제 장치를 두었습니다.

* **기준선 상수 87개 자동 대조:** 팀장이 확정한 기준선의 상수 87개를 실행 코드(`run_main.py`)의 값과 대조해서, 하나라도 다르면 시험이 실행되지 않습니다(`baseline_verification.csv`).
* **해시 고정과 버전 관리:** 기준선 파일은 SHA-256으로 고정했고(`sil_main/baseline/`), 변경이 필요하면 덮어쓰지 않고 버전을 올려 변경 전후 값을 남겼습니다.
* **자동 검증:** GitHub에 push하거나 Pull Request를 올릴 때마다 GitHub Actions(`.github/workflows/verify.yml`)가 `selftest.py`, 체크리스트, 문헌 지도를 검사합니다.
* **근거 없는 '충족' 차단:** `docs/29119/render_checklist.py`가 증빙이 연결되지 않은 항목을 '충족'으로 바꾸지 못하게 막고, 보고서의 수치는 결과 파일에서 다시 계산해 대조했습니다(`docs/29119/01_outcome_checklist.md`).
* **재현성 확인:** 같은 입력에서 같은 결과가 나오는지, 서로 다른 환경에서도 같은지 확인했습니다.
* **개인정보·저작권:** 공개 저장소에 올릴 때 팀원 실명을 마스킹했고, AI와의 대화 캡처와 논문 PDF, 논문에서 가져온 그림 16개는 올리지 않았습니다.

## 5. 한계점 및 실제 오류 수정 이력

### 프로젝트의 구조적 한계

1. **요구사항 도출의 AI 의존:** 검증 분야에 대한 초기 이해도가 낮아 요구사항 수치를 팀이 독자적으로 설계하지 못하고 AI의 제안에 크게 의존했습니다. 이를 보완하려고 문헌을 직접 선별하고 모든 수치에 출처 구분을 달았습니다.
2. **이해와 수행의 차이:** AI가 작업을 쉽게 해 준 것과 팀이 그 내용을 이해하는 것은 다르다고 보았고, 그래서 개념을 익히는 데 AI를 많이 썼습니다.
3. **가상 환경 검증의 한계:** 이번 시험 결과는 SIL 모델과 가상 반사면 입력에 대한 것이며 실제 센서의 성능을 입증하지는 못합니다.
4. **작성자와 검토자의 동일성:** 문서를 쓴 AI가 1차 수치 대조(AI 검토)도 수행했습니다. 팀원의 검토와 Pull Request 승인으로 보완했지만 독립 검토는 아닙니다.

### 작업 중 발견해 바로잡은 AI 오류

AI가 항상 정확했던 것은 아니며, 발생한 오류는 숨기지 않고 기록한 뒤 고쳤습니다.

* **증거 위치 누락:** AI가 저장소 파일만 보고 증거가 없다고 잘못 판단한 적이 있어, Notion에 기록된 내용을 확인해 정정했습니다.
* **검증 스크립트 오류:** TM-05 대조에서 스크립트가 범위 표기("TC-01~05")를 잘못 읽어 불일치로 판정한 것을 발견하고 원인을 확인해 바로잡았습니다.
* **낡은 승인 문구:** 공통 정보 표의 승인 기록이 갱신되지 않고 남아 있던 것을 팀장이 질문으로 확인했고, 하단 추가 기록으로 명시했습니다(`docs/29119/environment/TER-01.md`).
* **승인 시각:** Pull Request #9의 두 번째 승인이 병합 17초 뒤에 제출된 사실도 체크리스트에 그대로 남겼습니다.
* **레이아웃 확인:** AI는 문서를 화면으로 렌더링하는 도구가 없어 최종 보고서와 발표자료의 배치를 확인하지 못했습니다. 최종 보고서는 팀장이 Word에서 직접 열어 고쳤고, 발표자료의 배치는 사람이 확인해야 하는 항목으로 안내했습니다.

## 6. [참고] 발표 및 질의응답(Q&A) 대비 정리

> 실제로 한 일에 맞춰 말씀하시도록 기록과 설명을 바탕으로 정리한 초안입니다. 기억과 다른 부분은 고쳐서 말씀하세요.

**Q. 이번 프로젝트에서 AI를 어떤 방식으로 활용했나요?**

> Anthropic의 Claude를 사용했습니다. 처음에는 SIL 검증을 어떻게 진행해야 할지 몰라 AI에 전체 구조를 맡기다시피 했습니다. 하지만 초안을 읽고 되묻고, 검증 실무를 아는 팀원에게 물어 가면서 검증의 개념과 현업 흐름이 잡혔고, 그 뒤로는 AI와 대화하며 방향을 조율하는 방식으로 바뀌었습니다. ISO 29119를 우리 프로젝트에 맞게 테일러링하고 GitHub로 형상 관리를 하기로 한 것도 그 과정에서 정했습니다. 저에게 AI는 일을 대신 시키는 도구라기보다 검증이라는 낯선 분야의 개념을 익히는 도구에 가까웠습니다.

**Q. 요구사항은 팀에서 직접 만든 건가요, AI가 만든 건가요?**

> AI가 도출했습니다. 처음 해 보는 검증이라 백지에서 요구사항을 설계하기에는 이해도가 부족했습니다. 대신 AI가 관련 문헌을 조사하면 저희가 초록과 범위, 결론을 읽고 프로젝트 목표에 맞는 문헌만 골라서 다시 AI에 제공했습니다. 그 문헌을 근거로 요구사항을 뽑았고, 수치마다 문헌에서 온 것인지, 저희의 선택인지, 가정인지 구분해 표시해 두었습니다.

**Q. 그렇다면 팀에서 직접 판단하고 결정한 것은 무엇인가요?**

> 주제와 검증 방향을 정했고, 근거 문헌을 직접 선별했습니다. 시험을 돌리기 전에는 비어 있던 입력 항목 8가지를 결정했고, 결과가 나온 뒤에는 같은 높이의 화물을 구분하지 못하는 한계를 알고리즘을 바꾸지 않고 한계로 받아들였습니다. 온도 보정 채택과 마감에 따른 범위 축소도 저희가 결정했습니다. 또 AI가 쓴 글이 너무 티가 나서 최종 보고서는 제가 직접 고쳤습니다.

**Q. AI가 짠 시험 코드와 결과 수치를 어떻게 신뢰할 수 있나요?**

> 제가 확정한 기준선 상수 87개를 코드와 자동으로 대조해서, 하나라도 다르면 시험이 실행되지 않게 했습니다. 같은 입력에서 결과가 똑같이 나오는지, 다른 컴퓨터에서도 재현되는지 확인했고, 코드가 바뀔 때마다 GitHub이 자동으로 검사를 다시 돌립니다.

**Q. AI가 잘못 판단하거나 실수한 적은 없었나요?**

> 있었습니다. 증거가 있는 위치를 못 보고 없다고 답한 적, 검증 스크립트가 범위 표기를 잘못 읽은 적, 승인 후 갱신하지 않은 낡은 문구를 남긴 적이 있습니다. 발견할 때마다 원인을 확인해 고쳤고, 그 과정도 문서에 기록해 두었습니다.

**Q. AI를 쓰지 않는 팀원들과는 어떻게 협업했나요?**

> 문*호 팀원은 AI를 거의 쓰지 않는 대신 소프트웨어 검증 실무 경험으로 제 질문에 답하고 아이디어를 주셨고, 덕분에 AI에게 더 구체적으로 요청할 수 있었습니다. 강**엘 팀원은 AI가 쓴 보고서와 내용을 검토하고 수정하는 일을 맡아 완성도를 높여 주셨습니다. 두 분 모두 Pull Request에서 승인해 주셨습니다.

**Q. AI 없이도 이 프로젝트를 완수할 수 있었을까요?**

> 주어진 일정과 초기 이해도로는 쉽지 않았을 것입니다. 다만 AI가 작업을 빠르게 해 준 것과 저희가 그 내용을 이해하는 것은 별개라고 생각해서, 개념을 익히고 기준을 세우며 결과를 확인하는 데 시간을 썼습니다.
